# TODO: Import API — Session-Generated Record Imports via API

**Date noted:** 2026-11-09
**Status:** Deferred. Interim SQL stopgap in place for seanchaí (see below).

## The problem

During a research session, Claude generates structured records that belong in
the database — new ledger entries, updated notes, linked citations. Right now,
the only path to get those records in is a hand-written SQL INSERT file applied
directly with `psql`. That violates the core architectural rule:

> **Everything goes through the API. No direct database access ever.**

We need a proper import path that runs through `api.*` stored procedures and a
FastAPI endpoint, so session output can be ingested the same way the UI writes
records: through the write path that `web_app_user` is authorized to use.

This is not a seanchaí-only problem. Every Curator role that involves research
or data collection (genealogy, client intake, inventory, journalism) will need
the same thing.

---

## Current interim stopgap (seanchaí only)

Branch `session-2026-11-08-moorhead` in `carolynboyle/seanchai` contains:

```
data/imports/2026-11-08_moorhead-coal-tract.sql
```

This file contains INSERTs for PR-058 through PR-061 and UPDATE appends to
PR-039 and PR-051. It is applied with:

```bash
DB="docker compose exec -T db psql -U steward -d wcyj -v ON_ERROR_STOP=1"
$DB < data/imports/2026-11-08_moorhead-coal-tract.sql
```

This stopgap is acceptable only for seanchaí research data on a mesh-only
instance. It must be replaced before business data enters the database or
before `web_app_user` least-privilege is restored.

## What to build

### 1. Stored procedure: `api.import_records(jsonb[])`

A new stored procedure that accepts an array of JSONB record descriptors and
loops through them, calling the existing `api.save_record()` for each one.
Error handling should be transactional: fail the whole import or allow
per-record error collection depending on the `on_error` parameter.

**Signature (sketch):**

```sql
CREATE OR REPLACE FUNCTION api.import_records(
    p_records   jsonb[],
    p_dry_run   boolean DEFAULT false,
    p_on_error  text    DEFAULT 'abort'  -- 'abort' | 'skip'
)
RETURNS jsonb   -- { imported: n, skipped: n, errors: [...] }
LANGUAGE plpgsql
...
```

If `p_dry_run` is true, validate every record against the same rules
`api.save_record()` enforces, return what would happen, and roll back — no
data is written.

**Grant:** After adding this function, `06d_api_grants.sql` must be re-run
(EXECUTE grants on `api.*` are a snapshot, not standing policy).

### 2. FastAPI route: `POST /import`

A new route that:
- Accepts a JSON body: `{ "records": [...], "dry_run": false, "on_error": "abort" }`
- Calls `api.import_records()` via the existing DB connection
- Returns the result JSON (count, errors)
- Requires auth (session or API key — whatever the existing write routes use)
- Lives in its own module: `app/routes/import_routes.py`

The route should be scoped per module. A seanchaí import goes to
`POST /seanchai/import`; the underlying procedure is shared.

### 3. JSON payload format for Claude-generated output

Instead of generating SQL, Claude generates a JSON file at the end of a
research session. Format mirrors the `api.save_record()` payload:

```json
{
  "schema": "seanchai",
  "generated": "2026-11-08",
  "session": "moorhead-coal-tract",
  "records": [
    {
      "record_id": "PR-058",
      "record_type": "PR",
      "record_status": "needs_review",
      "display_order": 105,
      "year": "1854-05-13",
      "subject": "Mortgage — Boyle to Moorhead — May 13 1854",
      "county": "Washington County",
      "state": "PA",
      "source_citation": "Washington County Deed Books — Book and page TBD",
      "source_url": "",
      "notes": "..."
    }
  ],
  "updates": [
    {
      "record_id": "PR-039",
      "append_notes": "SESSION 2026-11-08 — ..."
    }
  ]
}
```

The `updates` array handles note appends — the equivalent of the current
`UPDATE ... SET notes = notes || ...` pattern — without requiring the caller
to know the full existing note value.

### 4. Optional UI: import panel per module

A simple file-upload panel on the seanchaí (and later other module) pages:
- Choose a `.json` file generated by Claude
- Dry-run preview: shows what would be inserted / updated
- Confirm → submits to `POST /seanchai/import`
- Result summary with per-record status

This is a "nice to have" — the endpoint is useful from the CLI or via `curl`
without any UI.

## Done when

  through `api.save_record()`.
- `web_app_user` has EXECUTE on `api.import_records` and no direct table access.
- The seanchaí SQL stopgap files in `carolynboyle/seanchai/data/imports/` are
  applied and their replacement path is the new endpoint.
- Dry-run mode works: calling with `"dry_run": true` returns a preview and
  writes nothing.
- The handoff template Claude uses at the end of a session outputs `.json`,
  not `.sql`.
