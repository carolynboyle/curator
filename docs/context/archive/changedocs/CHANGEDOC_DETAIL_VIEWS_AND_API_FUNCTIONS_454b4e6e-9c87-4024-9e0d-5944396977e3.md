# Changedoc: Detail views + `api.get_*_detail()` functions

**Date:** 2026-07-01
**Reason:** Step 2 of the fetch-and-swap detail-panel plan. Two things,
bundled because they're the same concern (the read path for the detail
panel) but kept SQL-only — no Python, no templates, no JS in this pass.

1. Closes the `web_app_user`/api-only inconsistency: `crew.py`'s (now
   `projects.py`/`contacts.py`/`organizations.py`'s) `_fetch_*_for_display`
   functions currently query `projects.projects` / `identity.contacts` /
   `identity.organizations` directly, which contradicts
   `06a_api_auth.sql`'s stated security model. New reads go through
   `api.get_*_detail()`, matching how writes already go through
   `api.save_*()`.
2. Gives the eventual field-schema system (`fieldkit`) something to
   introspect: `v_*_detail` views are a deliberate whitelist of exactly
   the columns each entity's detail form should show — see the new
   `sql_conventions.md` for the reasoning. Column order in each view is
   the field order the form will render in.

**Scope check against `project_rules.md`:** no hardcoded values, single
canonical implementation (Python doesn't duplicate what the view already
defines), database-first (verify in pgAdmin before any Python changes in
the next changedoc). No exceptions to flag.

**New numbered files, not edits to already-applied ones** — per the
convention just written down in `sql_conventions.md`.

---

## 1. `07_detail_views.sql` (new)

**Why these columns specifically:** each view is exactly the fields that
belong on that entity's detail form — `id` included (needed to know which
record you're looking at), `*_by` columns excluded (server-stamped, never
form fields), and for `projects.projects`, `slug` also excluded even
though nothing about its data type would otherwise flag it — it's
server-generated by `api.save_project()` and was never meant to be
directly editable. `notes` is included on contacts and organizations even
though the template doesn't render it yet (see the 2026-07-01 handoff's
"someday" list) — `api.save_contact()`/`api.save_organization()` already
accept it, so the view being ready now means the template gap is the only
remaining piece when that gets built.

```sql
-- =============================================================================
-- 07_detail_views.sql — Detail-panel-backing views
-- =============================================================================
--
-- One view per entity the detail panel can display: a deliberate
-- whitelist of exactly the columns that belong on that entity's
-- data-entry form. Not "the table minus a few exclusions" — id and *_by
-- columns are never included, and server-generated fields the user
-- shouldn't edit directly (e.g. projects.projects.slug) are left out
-- even though their data type wouldn't otherwise flag them.
--
-- Column order in each SELECT list is meaningful: it's the field order
-- the detail panel will render in once the field-schema system
-- introspects these views. Reordering a form's fields means reordering
-- the view here, not touching Python or template code.
--
-- See docs/sql_conventions.md for the full whitelist rationale.
--
-- Depends on: 02_identity.sql, 03_projects.sql
-- =============================================================================

CREATE VIEW projects.v_project_detail AS
SELECT
    id,
    name,
    description,
    type_id,
    status_id
FROM projects.projects;

CREATE VIEW identity.v_contact_detail AS
SELECT
    id,
    name,
    title,
    notes
FROM identity.contacts;

CREATE VIEW identity.v_organization_detail AS
SELECT
    id,
    name,
    notes
FROM identity.organizations;


-- =============================================================================
-- GRANTs
-- steward already has broader SELECT access to the underlying tables
-- (02_identity.sql, 03_projects.sql) — granting on these views too for
-- the same reason the role-filtered list views (captain_view etc.) are
-- granted: pgAdmin browsability without needing steward to know which
-- underlying table backs a view.
-- web_app_user gets nothing here — all access is through api.get_*_detail()
-- (07_detail_api.sql), consistent with the api-only read/write model.
-- =============================================================================

GRANT SELECT ON
    projects.v_project_detail
TO steward;

GRANT SELECT ON
    identity.v_contact_detail,
    identity.v_organization_detail
TO steward;
```

## 2. `07_detail_api.sql` (new)

**Why `LANGUAGE sql` instead of `plpgsql`:** each function is a single
`SELECT`, no branching or error handling needed — a not-found id just
returns `NULL`, same contract the old `_fetch_*_for_display` Python
functions already had (`db.fetch_one()` returning `None`), so the calling
route's `if not record: raise HTTPException(404, ...)` doesn't change.
`plpgsql`'s `DECLARE`/`BEGIN`/`EXCEPTION` scaffolding would be pure
overhead for a pass-through read.

```sql
-- =============================================================================
-- 07_detail_api.sql — API schema: get_*_detail() read functions
-- =============================================================================
--
-- Reads for the detail panel, routed through api.* the same way writes
-- already are — closes the gap where crew.py's old _fetch_*_for_display
-- functions queried projects.projects / identity.contacts /
-- identity.organizations directly, contradicting the api-only model
-- stated in 06a_api_auth.sql's header.
--
-- Each function returns the corresponding v_*_detail row as JSONB via
-- row_to_json(), or NULL if the id doesn't exist. Callers (Python routes)
-- check for None/null the same way they already do for the old direct
-- fetch functions — no change to error-handling shape.
--
-- Depends on: 07_detail_views.sql
-- GRANTs: web_app_user needs 06d_api_grants.sql re-run after this file —
-- the existing wildcard GRANT is a snapshot, it does not retroactively
-- cover functions created after it ran. See bottom of this file.
-- =============================================================================

CREATE OR REPLACE FUNCTION api.get_project_detail(p_id BIGINT)
RETURNS JSONB
LANGUAGE sql
SECURITY DEFINER
AS $$
    SELECT row_to_json(t)::jsonb
    FROM projects.v_project_detail t
    WHERE t.id = p_id;
$$;

CREATE OR REPLACE FUNCTION api.get_contact_detail(p_id BIGINT)
RETURNS JSONB
LANGUAGE sql
SECURITY DEFINER
AS $$
    SELECT row_to_json(t)::jsonb
    FROM identity.v_contact_detail t
    WHERE t.id = p_id;
$$;

CREATE OR REPLACE FUNCTION api.get_organization_detail(p_id BIGINT)
RETURNS JSONB
LANGUAGE sql
SECURITY DEFINER
AS $$
    SELECT row_to_json(t)::jsonb
    FROM identity.v_organization_detail t
    WHERE t.id = p_id;
$$;


-- =============================================================================
-- GRANTs — re-run, don't skip
-- The wildcard grant in 06d_api_grants.sql only covered functions that
-- existed in the api schema at the moment it ran. These three are new,
-- so without re-running this, web_app_user can EXECUTE every other
-- api.* function but gets a permission error on these three specifically
-- — an easy thing to chase as a mysterious bug if this step is skipped.
-- =============================================================================

GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA api TO web_app_user;
GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA api TO steward;
```

## Apply order

1. Run `07_detail_views.sql` in pgAdmin against `wcyj`.
2. Verify each view directly: `SELECT * FROM projects.v_project_detail
   WHERE id = <some real id>;` (and the same for contacts/organizations)
   — confirms the whitelist looks right before any function wraps it.
3. Run `07_detail_api.sql` — includes the `06d` grant re-run at the
   bottom, so this step alone is sufficient; no separate grants step.
4. Verify grants landed: `SELECT grantee, routine_name FROM
   information_schema.routine_privileges WHERE routine_name LIKE
   'get_%_detail';` — should show both `web_app_user` and `steward` for
   all three.
5. Smoke-test each function directly in pgAdmin: `SELECT
   api.get_project_detail(<id>);` — confirm it returns the expected JSON
   shape, and `SELECT api.get_project_detail(999999);` returns `NULL`
   for a nonexistent id.

No Python changes in this pass — `projects.py`/`contacts.py`/
`organizations.py`'s `_fetch_*_for_display` functions keep querying the
tables directly for now. Wiring them to call `api.get_*_detail()` instead
is the next changedoc, once these are confirmed working from pgAdmin
directly.
